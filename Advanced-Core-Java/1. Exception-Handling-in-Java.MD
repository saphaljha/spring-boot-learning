# Exception Handling in Java

A comprehensive deep dive into the Java exception hierarchy, runtime handling semantics, and production-grade error management patterns for enterprise backend systems.

---

## 1. Exception Hierarchy: Checked vs. Unchecked

Java organizes errors and exceptions under a single class hierarchy rooted in `java.lang.Throwable` [cite: 1, 3]:

```
                       +-----------------------+
                       | java.lang.Throwable   |
                       +-----------------------+
                                  |
              +-------------------+-------------------+
              |                                       |
    +-------------------+                   +-------------------+
    |  java.lang.Error  |                   |java.lang.Exception|
    +-------------------+                   +-------------------+
    (OutOfMemoryError,                       |                 |
     StackOverflowError)                     |                 |
     [Unchecked: Fatal]                      |                 |
                                             |                 |
                             +---------------+                 +---------------+
                             |                                                 |
                   +-------------------+                             +-------------------+
                   | Checked Exceptions|                             | RuntimeException  |
                   +-------------------+                             +-------------------+
                   (IOException,                                     (NullPointerException,
                    SQLException)                                     IllegalArgumentException)
                   [Enforced at compile-time]                        [Unchecked: Logic errors]
```

### Categorization

1. **`Error` (Unchecked / Fatal):**
   * Severe conditions external to normal program logic (e.g., `OutOfMemoryError`, `StackOverflowError`).
   * Should never be caught in application code.
2. **Checked Exceptions (`Exception` excluding `RuntimeException`):**
   * Recoverable external failure conditions (e.g., network timeout, missing file, SQL error).
   * **Compiler-enforced:** You must either handle them via `try-catch` or declare them in the method signature via `throws` [cite: 1, 3].
3. **Unchecked Exceptions (`RuntimeException` and subclasses):**
   * Programmatic and logic errors (e.g., `NullPointerException`, `IndexOutOfBoundsException`, `IllegalArgumentException`).
   * Do not require explicit handling or signature declarations.

## 2. Keywords: `try`, `catch`, `finally`, `throw`, and `throws`

* `try`: Encloses code that could raise an exception [cite: 1, 3].
* `catch`: Handles the specific exception type. Can use multi-catch blocks (`catch (TypeA | TypeB e)`).
* `finally`: Guaranteed execution block. Executes regardless of whether an exception occurred, even if a `return` is executed inside `try` or `catch`.
* `throw`: Explicitly triggers an exception instance (e.g., `throw new IllegalArgumentException(...)`).
* `throws`: Method signature declaration alerting callers to potential checked exceptions [cite: 1, 3].

### Code Example: Syntax & Multi-Catch

```java
package com.roadmap.exceptions;

import java.io.IOException;
import java.sql.SQLException;

public class BasicExceptionHandlingDemo {

    public static void main(String[] args) {
        try {
            processPaymentRecord("ORD-9021", -50.0);
        } catch (IllegalArgumentException ex) {
            System.err.println("Client validation failed: " + ex.getMessage());
        } catch (IOException | SQLException ex) {
            // Multi-catch: handles related checked exceptions cleanly
            System.err.println("Infrastructure communication error: " + ex.getMessage());
        } finally {
            // Always executes (used for resource teardown in pre-Java 7 legacy code)
            System.out.println("Execution completed.");
        }
    }

    public static void processPaymentRecord(String orderId, double amount) 
            throws IOException, SQLException {
        if (amount <= 0) {
            throw new IllegalArgumentException("Amount must be positive: " + amount);
        }
        // Simulated I/O or DB operation
    }
}
```

## 3. `try-with-resources` & the `AutoCloseable` Interface

Introduced in Java 7, `try-with-resources` eliminates manual resource management (closing files, database connections, streams) inside `finally` blocks [cite: 1, 3].

### How It Works

Any object implementing `java.lang.AutoCloseable` (or `java.io.Closeable`) declared in the `try (...)` parenthesis is automatically closed when execution leaves the block, even if an exception or `return` occurs.

```java
package com.roadmap.exceptions;

import java.io.BufferedReader;
import java.io.FileReader;
import java.io.IOException;

public class TryWithResourcesDemo {

    // Automatically closes BufferedReader and FileReader without explicit finally blocks
    public static String readFirstLine(String path) throws IOException {
        try (BufferedReader reader = new BufferedReader(new FileReader(path))) {
            return reader.readLine();
        }
    }

    // Custom AutoCloseable resource
    static class DatabaseConnectionSession implements AutoCloseable {
        public void execute(String sql) {
            System.out.println("Executing SQL: " + sql);
        }

        @Override
        public void close() {
            System.out.println("Database connection released back to HikariCP pool.");
        }
    }

    public static void main(String[] args) {
        try (DatabaseConnectionSession session = new DatabaseConnectionSession()) {
            session.execute("SELECT * FROM orders WHERE id = 1");
        } // session.close() is called automatically here
    }
}
```

## 4. Designing Custom Domain Exceptions

In Spring Boot and modern Java, modern backend design favors a clear hierarchy of **unchecked** domain exceptions that map to HTTP responses or domain state transitions [cite: 2, 3].

```java
package com.roadmap.exceptions;

// Base domain exception (Unchecked)
public abstract class DomainException extends RuntimeException {
    protected DomainException(String message) {
        super(message);
    }

    protected DomainException(String message, Throwable cause) {
        super(message, cause); // Preserves the original stack trace (Root Cause)
    }
}
```

```java
package com.roadmap.exceptions;

// Specialized business error
public class ResourceNotFoundException extends DomainException {
    private final String resourceName;
    private final String identifier;

    public ResourceNotFoundException(String resourceName, String identifier) {
        super(String.format("%s with identifier '%s' was not found", resourceName, identifier));
        this.resourceName = resourceName;
        this.identifier = identifier;
    }

    public String getResourceName() {
        return resourceName;
    }

    public String getIdentifier() {
        return identifier;
    }
}
```

```java
package com.roadmap.exceptions;

// Specialized business conflict error
public class InsufficientStockException extends DomainException {
    private final String sku;
    private final int requested;
    private final int available;

    public InsufficientStockException(String sku, int requested, int available) {
        super(String.format("Insufficient stock for SKU '%s'. Requested: %d, Available: %d", 
                sku, requested, available));
        this.sku = sku;
        this.requested = requested;
        this.available = available;
    }

    public String getSku() {
        return sku;
    }

    public int getRequested() {
        return requested;
    }

    public int getAvailable() {
        return available;
    }
}
```

## 5. Anti-Patterns & Best Practices

| Anti-Pattern | Why It Breaks Applications | Production Alternative |
| :--- | :--- | :--- |
| **Swallowing Exceptions**<br>`catch (Exception e) {}` | Hides critical system bugs and renders debugging impossible. | Log the error using SLF4J or rethrow a wrapped `DomainException`. [cite: 1] |
| **Catching `Throwable` or `Error`** | Catches fatal JVM errors (`OutOfMemoryError`) that the app cannot recover from. | Catch specific subclasses (`Exception` or custom domain types). |
| **Losing the Root Cause**<br>`throw new CustomException(e.getMessage())` | Drops the original stack trace, making tracing root issues difficult. | Always pass the cause: `throw new CustomException("msg", e)`. |
| **Using Exceptions for Normal Control Flow** | Constructing a stack trace requires significant CPU overhead. | Use conditional checks (`if-else`) for predictable validations. |

## 6. Key Takeaways for Magento / PHP Developers

1. **Checked Exceptions Do Not Exist in PHP:** PHP exceptions are all unchecked (they behave like Java's `RuntimeException`). In Java, external operations (file access, network sockets) force you to declare `throws` or catch the error explicitly [cite: 1, 3].
2. **Exception Bubbling in Spring Boot:** Magento often uses `LocalizedException` which is caught in layout/block layers. In Spring Boot, domain exceptions bubble directly up to `@RestControllerAdvice` where they translate into clean HTTP status codes (e.g., `404 Not Found`, `400 Bad Request`) [cite: 1, 2, 3].
